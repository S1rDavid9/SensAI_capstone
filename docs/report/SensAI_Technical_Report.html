1. What SensAI is

SensAI is a web app for learners aged 8 to 14 that adapts short maths and pattern puzzles to how a learner is working. After every answer it runs a closed loop: Stage 1, a classifier, estimates a behavioural state from the last five answers (on task, rushing/under-challenged, or struggling/needs support); Stage 2, a Deep Q-Network (DQN) trained in simulation, chooses one of eight scaffolding actions; guardrails rule out actions no teacher would choose; and the app applies the action by choosing the next question and showing a short message or hint. Engagement is treated strictly as observable behaviour (Fredricks et al., 2004): the system does not claim to detect emotions. This milestone delivers the simulation and policy (Phase 1), the data-collection pilot with 31 learners at Excella School, Kigali, the Stage 1 classifier trained on that data, and the closed-loop adaptive app as the final MVP.

3. Technical implementation

Figure 1. Request path for one answer. Each box is a class or module; arrows show dependencies (top-level wiring is in create_app).

Backend/frontend interaction. The React (TypeScript) screens talk to a FastAPI backend over JSON. The learner screen sends an event when a question is shown, at the first keystroke, every 20 seconds without input, and on leaving the window, then posts the answer with client-measured timings. The server grades it, stores it, runs Stage 1 → Stage 2 and, in adaptive mode, stores the next question and the support message, which the next /question call returns. Devices synchronise clocks with /api/time (offset taken from the lowest round-trip of three samples) so observations from phones line up with laptop events.

Algorithms and problem-solving

  • DQN policy (Mnih et al., 2015): a 9 → 64 → 64 → 8 Q-network with experience replay and a target network, trained on 20,000 simulated steps. The pilot revealed two reward loopholes: alternating advance topic (bonus) with decrease difficulty, and moving on when a learner was confused. Simulator v2 withholds the topic bonus in both cases and makes advancing while confused more likely to keep the learner confused. Result: "confused → move on" fell from 69% to 0% of decisions on held-out seeds; v1 still reproduces exactly (8.50 mean reward). PPO, A2C and REINFORCE collapsed to one or two actions under v2, even with five times the training budget for PPO, so DQN is the policy carried forward.
  • Shielding (Alshiekh et al., 2018): Shield.decide masks forbidden actions and takes the arg-max of the remaining Q-values. Both the raw and the shielded action are stored, so results can be reported with and without guardrails.
  • Stage 1: features from a sliding window of the last five answers; standardised logistic regression with balanced class weights. Error rate and response time follow prior work on response-time effort and disengagement (Beck, 2005; Wise & Kong, 2005) and on gaming behaviour (Baker et al., 2004).
  • Curriculum planner: each action maps to a target level and a question-type rule; the planner searches levels outward from the target (target, ±1, ±2), prefers the requested type, never repeats a question, and rewrites the message when the bank cannot move as intended (for example "easier" at level 1).

Validation results on the pilot data

Signals vs labels. Error rate in the five questions before a check-in separated "hard/lost" from other answers by 1.46 standard deviations within the same block (p = 0.0001). Response time alone did not, because the two struggling answers behaved oppositely: "hard" was slow (median 69 s), "lost" was fast with 74% errors, consistent with rapid guessing (Wise & Kong, 2005). Stage 1 (leave-one-learner-out, 92 labelled blocks): balanced accuracy 0.67 against 0.33 for the majority baseline; AUC 0.90 for "needs support". Adding more features lowered accuracy (all seven: 0.58; shallow XGBoost: 0.47), so the deployed model uses error rate and response time only. Stage 1 → DQN on the 463 real answers: under-challenged → move on (76%) or challenge (20%); needs support → simplified repeat (52%), easier (29%), encourage (19%); on task → the DQN chose "easier" 70% of the time, which the guardrail blocked (21.8% of all decisions shielded). On-task behaviour is the policy's known weak spot.

5. Code quality and OOP practice

  • Layered architecture and separation of concerns: core (domain), labelling, policy, adaptation, storage, services, api. Routes contain no logic; services raise domain errors (NotFound, Conflict…) that one handler maps to HTTP.
  • Abstraction and polymorphism: StateLabeler (implemented by RuleBasedLabeler and Stage1Labeler), ActionScorer (DQNPolicy, and a fake scorer in tests), GuardrailRule (StateRule, DifficultyBoundsRule) and SessionMode (ShadowMode, AdaptiveMode: the Strategy pattern). Inheritance is used only for these interfaces.
  • Encapsulation and SOLID: one repository per table hides SQL; a Database class owns connections and upgrades. New rules or labellers are added without changing existing classes (open/closed); services receive their collaborators in create_app (dependency inversion), which is what makes them testable with fakes.
  • Readability and maintainability: consistent names (BehaviouralState, CurriculumPlanner), frozen dataclasses for value objects, module docstrings explaining why, settings read once from the environment, and a commit history describing each change.

6. Ethics, limitations and next steps

The pilot ran under ALU Research Ethics Committee approval with guardian consent and learner assent; learners are known only by codes, and no cloud service receives their data. During the pilot the DQN never affected learners: everyone saw the same 15 questions and the policy's decisions were only stored. Adaptive mode is demonstrated by the researcher; using it with children needs a new approval. Limitations: one school and one session per learner; only 11 "hard"/"lost" check-ins; observations too sparse for inter-rater agreement; more learners than the approved 10–20 (a deviation from the approved protocol); plausibility ratings still pending; and REINFORCE results are not reproducible. Next: rate the plausibility sheet with the class teacher, run a smaller observation session for paired codes, and seek approval to evaluate adaptive mode with learners.
